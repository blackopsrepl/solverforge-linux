SolverForge Linux — wiring at a glance

one source of truth → templates → generated → symlinked into ~/.config → apps read it

The rule that keeps it coherent

  • • colors.toml is the only place a color exists.
  • • default/ is immutable — templates and static configs live there.
  • • generated/ is derived and gitignored — never hand-edit.
  • • ~/.config/* holds symlinks, not files. Edit the source, re-run solverforge-theme-apply.
  • • One exception: swaync/style.css is copied, because swaync can't follow symlinks.

Provisioning path

  • • boot.sh (curl | bash) clones or fast-forwards the checkout, then execs install.sh.
  • • Fresh vs update is decided by ~/.config/sway/config.d/solverforge.conf existing.
  • • Phases 0*.sh are sourced into one shell: preflight → packages → config → theme → skill → post.
  • • Package manager is zypper; the installer refuses to run as root.

Runtime path

  • • Sway sources the orchestrator, which includes the default layer plus generated colors.
  • • autostart.conf launches tray, waybar and the companion supervisor via exec_always.
  • • Every waybar custom module is a solverforge-waybar-* command on PATH.
  • • PATH and SWAYLOCK_CONFIG come from environment.d; zsh sources the 10 shell files in order.

Agent surface

  • • skills/solverforge-linux/ is the domain authority for this framework.
  • • scripts/install-skill lands it per harness with .solverforge-skill ownership markers.
  • • 03-config.sh sets OPENCODE_DISABLE_CLAUDE_CODE=1, which disables opencode's ~/.claude/skills scan.

Hazards

  • • Editing generated/* or a symlink target in ~/.config gets overwritten on the next apply.
  • • This checkout is not the live install — exercise it with SOLVERFORGE_PATH="$PWD".
  • • *.db, .claude/, mail/, generated/ are gitignored local state.
